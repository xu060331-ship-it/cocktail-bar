## 三、Nginx 配置（最终版）

```nginx
# HTTP 80 端口 —— 全部跳转 HTTPS
server {
    listen 80;
    server_name cocktail-bar.cn www.cocktail-bar.cn;
    return 301 https://$host$request_uri;
}

# HTTPS 443 端口 —— 主服务
server {
    listen 443 ssl;
    server_name cocktail-bar.cn www.cocktail-bar.cn;

    ssl_certificate     /etc/nginx/cert/cocktail-bar.cn.pem;
    ssl_certificate_key /etc/nginx/cert/cocktail-bar.cn.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;

    # 视频文件 CORS（解决 Chrome Private Network Access 拦截）
    location ~* \.(mp4|webm|ogg)$ {
        add_header Access-Control-Allow-Origin *;
        add_header Access-Control-Allow-Private-Network true;
        root /root/cocktail-bar/frontend-react/dist;
    }

    # API 反向代理
    location /api/ {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # AI 流式对话（SSE）必须关闭缓冲
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
    }

    # 前端静态资源
    location / {
        root /root/cocktail-bar/frontend-react/dist;
        index index.html;
        try_files $uri /index.html;
    }
}
```

### 关键配置点

1. **`proxy_pass http://localhost:3000;` 不带斜杠**：完整保留 `/api/xxx` 路径传给后端（后端端点就是 `/api/` 前缀）。
2. **`proxy_buffering off` 是关键**：AI 流式对话用 SSE，如果 Nginx 缓冲了响应，前端会卡住等一次性返回，逐字打字效果消失。
3. **`try_files $uri /index.html`**：SPA 前端路由刷新不 404。

### 5.2 关键知识点

1. **解析到 IPv4（A 记录）**：服务器 39.96.28.21 是 IPv4，不要选 IPv6/AAAA。

4. **验证命令**：`nslookup cocktail-bar.cn` 或 `curl http://cocktail-bar.cn`。

## 六、SSL 证书 + HTTPS

### 6.1 证书申请

| 项目 | 值 |
|------|-----|
| 提供商 | 阿里云免费证书（DigiCert） |
| 类型 | 单域名证书 |
| 绑定域名 | cocktail-bar.cn（含 www 的 SAN） |
| 有效期 | 3 个月（2026-08-15 ~ 2026-11-12） |
| 验证方式 | DNS 验证 |
| 格式 | Nginx（.pem + .key） |

### 6.2 关键知识点

1. **免费证书 3 个月有效**：**11月12日前**必须续期，重新下载新证书 → 替换 `/etc/nginx/cert/` → `nginx -s reload`。
2. **证书文件包含证书链**：.pem 里有两段 `BEGIN CERTIFICATE`（叶子证书 + 中间证书），这是正常的，都要保留。
3. **单域名证书**：只覆盖 cocktail-bar.cn（含 www 的 SAN），不能覆盖其他子域名。
4. **`openssl s_client` 验证证书**：
   ```bash
   echo | openssl s_client -connect cocktail-bar.cn:443 -servername cocktail-bar.cn 2>/dev/null | openssl x509 -noout -subject -dates
   ```

### 6.3 证书传输的坑

- **scp 静默成功**：scp 上传成功时**不输出任何信息**，只回到提示符。看到进度条（`100%`）就是成功。
- **heredoc 粘贴卡住**：`cat > file << 'EOF' ... EOF` 如果最后 `EOF` 那行多了空格或少了换行，shell 会一直等待输入。按 `Ctrl+C` 退出，改用 nano 编辑器更可靠。

### 7.3 关键知识点（踩过的坑）

1. **「提供」vs「使用」AI 服务**：网站**调用** DeepSeek API 属于「使用」AI，不是「提供」AI。不需要「生成式人工智能备案」，但如实选了「信息深度合成」分类。
2. **表述要准确**：错误写「利用生成式AI提供服务」会让人以为你是 AI 平台；正确是「提供调酒知识服务，部分功能使用 AI 辅助内容生成」。
3. **域名服务商 ≠ 阿里巴巴通信技术**：后者是通信业务（短信/号码），域名注册是「阿里云计算有限公司/万网」。
4. **域名注册商确认**：whois 查询可查（阿里云企航 = 原万网）。
5. **提交后不能撤回**：填错等审核退回修改，或联系当地公安网安部门。
6. **提交了主体信息也要继续填网站信息**：两部分都提交才算完整申请，别半途而废。

## 九、AI 接入架构（部署视角）

### 9.1 纯手写，无 LangChain

AI 功能**零依赖**，靠 Node.js 原生 `fetch()` 直接调 DeepSeek：

```js
fetch("https://api.deepseek.com/v1/chat/completions", {
  method: "POST",
  headers: { Authorization: `Bearer ${DEEPSEEK_API_KEY}`, "Content-Type": "application/json" },
  body: JSON.stringify({ model: "deepseek-chat", messages, temperature: 0.7 }),
})
```

| 功能 | 实现方式 |
|------|---------|
| API 调用 | 原生 fetch |
| 流式输出 | 手写 SSE parser |
| 重试+降级 | try/catch + 切换通义千问 |
| JSON 解析 | 正则匹配 {} + JSON.parse |
| 引用校验 | Set 集合查 eng 是否在库 |

### 9.2 Provider 配置

| Provider | API 地址 | 用途 |
|----------|---------|------|
| deepseek | `https://api.deepseek.com/v1` | 主力 |
| qwen | `https://dashscope.aliyuncs.com/compatible-mode/v1` | fallback |

### 9.3 环境变量（backend/.env）

```
DATABASE_URL=postgresql://postgres:密码@localhost:5432/cocktail_bar
AI_PROVIDER=deepseek
AI_ENABLED=true
DEEPSEEK_API_KEY=sk-xxx
QWEN_API_KEY=xxx
```

> ⚠️ `.env` 在 `.gitignore` 里，**不上传 GitHub**。服务器部署时手动拷贝。
